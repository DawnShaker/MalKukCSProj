# Этапы 5–6: единое C# приложение

Основной вариант для демонстрации задания:

```text
React (формы и кабинеты)
    ↓ /api
C# контроллеры (проверка входа, роли и владельца записи)
    ↓
AgencyService / AccountService (правила агентства)
    ↓
AgencyDbContext / EfAgencyDataManager (Entity Framework Core)
    ↓
    SQLite локально / PostgreSQL Supabase на Render — общая база агентства

AccountController → SecurityClient → HTTP API Security преподавателя
```

Интерфейс и API раздаёт один ASP.NET Core сервер. Netlify Functions для этого запуска не нужны.
Пароли проверяет Security, а роли агентства и связи с клиентами/агентами хранятся в SQLite.

## Запуск на этом компьютере

Нужны Node.js 22+ и .NET SDK 10. Все команды выполняются из корня репозитория.

```powershell
npm.cmd ci
npm.cmd run agency:build
```

Локальный Security запускается в отдельном терминале:

```powershell
npm.cmd run security:prepare -- --username owner@example.com
npm.cmd run security:start
```

Если Security уже подготовлен, повторный `security:prepare` не меняет существующие пароль и ключ.
В другом терминале:

```powershell
npm.cmd run agency:start
```

Откройте <http://127.0.0.1:5000>. Логин и пароль администратора находятся в игнорируемом
`.local/security-config.json`. Вводите их в форме входа, не добавляйте в исходники.

При первом запуске создаётся `.local/agency.db`, применяется EF-миграция и импортируется
исходный `RealEstateAgency/agency_data.json`. Повторные запуски используют эту же БД.
Файлы ключей сессии находятся в `.local/agency-runtime/.local/keys`; они сохраняют действующие
сессии после перезапуска сервера. Не публикуйте их.

На компьютере, где уже выполнено облачное развёртывание из этой ветки, можно использовать
работающий HTTPS Security вместо локального:

```powershell
npm.cmd run agency:start -- --cloud-security
```

Команда читает адрес и JWT-настройки из `.local/deployment-state.json` и `.local/security-cloud.json`.
База самого агентства при этом остаётся локальной SQLite. Удалённая база аккаунтов Security — отдельное хранилище.
После простоя Render Free пробуждается не сразу: если первая попытка входа вернула временную недоступность Security, повторите её примерно через минуту.

## Финальное размещение

Netlify раздаёт интерфейс и пересылает `/api/*` в C# сервис Render Free. API использует
`Database__Provider=PostgreSQL` и закрытую схему `agency_ef` существующей Supabase. Это та же
бизнес-логика и EF Core, что в локальном запуске. Для PostgreSQL есть отдельный класс контекста
и отдельная начальная миграция; SQLite-миграции остаются для локального варианта.

В PostgreSQL хранится также таблица `DataProtectionKeys`. Поэтому перезапуск бесплатного
контейнера не удаляет данные и не меняет ключи cookie. Локальный диск Render не используется.
Для подключения включена проверка TLS с публичным CA Supabase, помещённым в контейнер.

Настройки описаны в `render-agency.yaml`; секреты задаются только в окружении Render.
Прежние таблицы схемы `public` сохраняются как копия до переключения. При переносе профиля
проверяется его соответствие подписанной учётной записи Security; совпадение email не назначает права.

## Роли

| Роль | Разрешённые действия |
|---|---|
| Менеджер | Все объекты, клиенты и сделки; создание агентов; статистика; CSV-отчёт; назначение ролей и ответственных агентов. |
| Агент | Только свои объекты, клиенты и сделки. Нельзя назначить запись другому агенту или открыть чужую по ID. |
| Клиент | Каталог доступных объектов; свои запросы, сохранённые фильтры, уведомления и история поисков. |

Первым менеджером становится только пользователь с подписанной ролью `Admin` в Security и логином
из `Security__BootstrapManagerUsername`, если менеджеров ещё нет. Форма входа не назначает роли.
Все остальные пользователи при первом входе получают роль клиента. Если логин уже связан
с другим идентификатором, сервер возвращает конфликт, а не объединяет аккаунты.

Для демонстрации нескольких ролей:

1. Создайте дополнительные аккаунты через API администратора Security. Локальный Swagger доступен на <http://127.0.0.1:5252/swagger>.
2. Войдите каждым аккаунтом хотя бы один раз: в БД агентства появятся его профиль и запись клиента.
3. В окне менеджера откройте **Користувачі**, назначьте роль агента и выберите соответствующего риелтора.
4. Назначьте ему объекты и клиентов через формы редактирования менеджера.
5. Откройте второй профиль браузера или приватное окно и войдите агентом/клиентом.

Роль читается из БД при каждом запросе. Поэтому смена роли действует и для уже выданной сессии.
Последнего менеджера нельзя понизить. Для каждой HTTP-операции создаётся новый `AgencyService`,
который читает актуальные строки из общей БД: разные окна не работают с отдельными JSON-копиями.

## Что именно сделано для этапа 5

- `IntegrationLayer/SecurityClient.cs` отправляет логин/пароль серверу преподавателя и проверяет подпись, issuer, audience и срок JWT стандартной библиотекой Microsoft.
- C# контроллер входа обращается к этому классу; JWT не передаётся браузерному JavaScript.
- `AgencyDbContext` и миграция создают таблицы и связи; `AgencyService` использует `EfAgencyDataManager`.
- JSON используется только для импорта/экспорта. Существующая непустая БД не перезаписывается импортом.
- Ответственный агент старых записей определяется по существующей сделке, только если связь однозначна.

## Что именно сделано для этапа 6

- Все предметные маршруты C# защищены `[Authorize]`.
- `AgencyAccess` проверяет роль и владельца записи до обращения к изменяющим методам бизнес-логики.
- `AccountService` хранит роли, назначает связи и защищает последнего менеджера.
- Добавлены C# маршруты кабинета клиента, истории поисков, управления пользователями и CSV-отчёта.
- Для сессии применяется стандартная HttpOnly-cookie ASP.NET Core. Все изменяющие запросы требуют antiforgery-токен.

Новые классы обычные: контроллеры, один HTTP-клиент, сервис аккаунтов и несколько методов проверки доступа.
CQRS, MediatR, универсальные репозитории и собственный формат токенов не используются.

## Проверка

```powershell
npm.cmd run agency:check
dotnet run --project tests/RealEstateAgency.PersistenceChecks --configuration Release
```

`agency:check` поднимает настоящий C# HTTP-сервер, временную SQLite и небольшой тестовый сервер
с тем же контрактом Security. Проверяются подпись/срок JWT, три роли, чужие ID, CSRF,
сохранённые поиски, отчёт, смена роли без повторного входа и сохранение данных после перезапуска.
Тестовые учётные записи существуют только в этом тесте; в рабочий Security они не добавляются.

Для обычной разработки интерфейса можно запустить `npm.cmd --prefix client-app run dev`:
Vite перенаправляет `/api` на C# сервер `127.0.0.1:5000`.

Отдельные Merge Request, отчёты по этапам и демонстрация преподавателю остаются частью сдачи из PDF.
